FD2.SAV current-runtime snapshot（IDA Pro 9.4）
================================================

證據範圍
--------

- `FD2.EXE`：357074 bytes
- MD5：`b97caf2239a27a896069d03549d96e1e`
- SHA-256：`222b7d067ad4450eb9c5f6e6bce1797d54bb050417ba39ced6067f8039f28c4f`
- 第一順位工具：合法 IDA Pro 9.4，使用者提供於
  `/home/anr2/ida_94_official/dist`，只在授權 Docker 映像執行。
- 原版與授權檔唯讀；IDA 資料庫只寫入 `/tmp/fd2-ida-runtime-save`，
  證據擷取後刪除。

此文件描述的是 `FD2.SAV` 內「繼續目前戰鬥」快照，不是四個章節存檔槽。
`FD2.SAV` 是可變檔案，不列入固定版本雜湊基準；下方實驗值只能作本次
使用者原版快照的動態旁證。

讀取端 `0x10010`
----------------

`0x10010` 驗證 checksum 後使用下列 plaintext 區域。早期文件只列出
兩份 roster 與 header，漏掉兩個直接複製的 raw 區域；下表已更正：

| plaintext offset | 長度 | 直接指令與目的地 |
|---|---:|---|
| `0x0000` | `0x08A3` | `0x101C3..0x101D7` 複製至 `[0x53A55]` 後呼叫 `0x10652` |
| `0x08A3` | `0x0A00` | `0x1010F..0x10121` 固定複製至 persistent roster `[0x53BF7]` |
| `0x12A3` | `header[1] * 0x50` | `0x10296..0x10311` 複製至 runtime roster `[0x53A45]` |
| `0x30A3` | `0x20` | `0x10319..0x10328` 複製至 `[0x53AD5]` 指向的 heap table；writer `0x1A03D..0x1A04C` 對稱保存。這是未命名 index 的 battle-local event state |
| `0x30C3` | `0x12` | 逐欄恢復目前戰鬥的標頭 |

18-byte header 的已證實映射：

| header offset | 目的地 | 狹窄名稱 |
|---|---|---|
| `+0` | `[0x53BEF]` | turn counter |
| `+1` | `[0x53BEB]` | runtime roster count |
| `+2` | `[0x53C03]` | chapter |
| `+3/+4` | camera globals | camera X／Y |
| `+5/+6` | absolute cursor globals | absolute cursor X／Y |
| `+7/+8` | visible cursor globals | visible cursor X／Y |
| `+9` | `[0x53BFB]` | persistent roster count |
| `+10..+13` | `[0x53BF3]` | currency dword |
| `+14` | `[0x53AF9]` | raw option |
| `+15` | `[0x51AAB]` | HUD gate A |
| `+16/+17` | `[0x51E61]/[0x51E62]` | raw options |

重要勘誤：舊版 `tools/fd2save.py` 曾把 `header[0]` 顯示為
`persistent_count`。IDA 直接指令證實該欄是 `[0x53BEF]` turn counter；
persistent count 在 `header[9]`，runtime count 在 `header[1]`。

CONTINUE 擁有權
---------------

第三標題分支與 `0x10010` 尾端的直接指令為：

    0x26124  push 0
    0x26126  push -1
    0x26128  call 0x25977
    0x26130  call 0x10010
    0x26135  push 0
    0x26137  mov  eax,[0x53C03]
    0x2613C  movzx eax,byte [eax+0x51E63]
    0x26144  call 0x25977

`0x10010` 不只複製資料；它依 header chapter 載入 FDFIELD／FDTXT／
FDSHAP，依 runtime record `+7` 建 selector，恢復 camera/cursor/options，
完成畫面演出後：

    0x10602  mov dword [0x53AE9],0
    0x1060C  mov dword [0x51A83],1
    0x10616  call 0x4E031
    0x1061B  jmp  0x22BBE

`0x10010` 的 prologue 保存 `ebx/esi/edi/ebp` 並配置 4-byte local；
`0x22BBE` 恰好執行 `add esp,4`、依反序恢復這四個暫存器再 `ret`。因此這是
刻意共用的函式 epilogue；不能因 IDA 把 `0x22BBE` 歸入鄰近函式，就誤認
為跳入另一個遊戲機制處理器（gameplay handler）。

動態原版快照實驗
----------------

2026-07-29 以使用者目前未修改的
`org_game/炎龍騎士團/FLAME2/FD2.SAV` 唯讀解碼：

- checksum 通過，plaintext size `0x59CB`
- header bytes：`01 0C 00 01 0D 08 11 07 04 04 00 00 00 00 00 01 01 01`
- turn counter `1`
- runtime count `12`
- chapter `0`
- persistent count `4`
- persistent records 的 raw identity 順序：`[0, 9, 4, 30]`
  （角色表對應索爾、悠妮、亞雷斯、蓋亞）
- 四個章節槽皆以 `chapter=0xFF` 顯示為空槽；空槽其餘 metadata 是垃圾值，
  不得作有效欄位解讀。

重製端邊界
----------

- `fdsave.InspectCurrentSnapshot` 保存上述五個固定區域；`0x0000` 已依
  FDFIELD 載入來源、對稱 writer／reader 與欄位 consumers 提升為
  `NativeFieldControl[0x8A3]`。`0x30A3` 已依 pointer allocation、對稱
  writer／reader 與 indexed consumers 提升為 `NativeEventState[32]`；
  各 index 的高階事件名稱仍不猜。
- runtime count 超過 96、persistent count 超過 32 時拒絕整份快照。
- persistent 與 runtime records 都保存原始 `0x50` bytes；高階角色名稱與
  `battle.Unit` 轉換仍需獨立、嚴格的 identity／class catalog。
- IDA Pro 9.4 與 Capstone 另證實 `0x10010` 自己載入章節資源、建立 runtime
  selector、恢復畫面，並在 `0x10616` 呼叫戰鬥驅動 `0x4E031`；`0x1061B`
  跳到 `0x22BBE` 是與其 prologue 配對的共享 epilogue，不是另一個未找到的
  CONTINUE owner。呼叫返回 `0x26135` 後只再依 `[0x53C03]` 查
  `0x51E63` 重設章節曲號。
- 重製端尚未有等價 production owner，真正缺口是
  `NativeFieldControl` 與 runtime record/selector、戰鬥規則狀態之間的
  一致性還原，不是
  header 章節欄位或 persistent record materializer。四槽 LOAD 仍是另一條
  `0x2CAD7→pre-handler` ABI，不可接到此解析器。

`[0x53AD5]` 指標與 current-save 對稱 copy 的勘誤／直接證據另見
[`fd2_current_event_state_ida.txt`](fd2_current_event_state_ida.txt)。
`0x0000` 控制映像的來源與 consumers 見
[`fd2_current_field_control_ida.txt`](fd2_current_field_control_ida.txt)。
