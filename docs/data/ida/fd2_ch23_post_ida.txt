FD2.EXE：raw ch23 post／玩家第24戰戰後處理器證據
====================================================

輸入基準
--------

- 檔名：FD2.EXE
- 大小：357074 bytes
- MD5：b97caf2239a27a896069d03549d96e1e
- SHA-256：222b7d067ad4450eb9c5f6e6bce1797d54bb050417ba39ced6067f8039f28c4f
- 第一順位工具：IDA Pro 9.4，資料庫線性位址
- 第二順位驗證：Capstone 5 Docker，`tools/disasm_le.py` 線性位址
- 本批 IDA 函式：`0x24c1e..0x24d22`、`0x24d22..0x24df2`、
  `0x17aa9`、`0x11d40..0x11df2`、`0x11eee`、`0x4dfcc`
- 註記方式：保留 IDA 原始名稱、線性位址與 raw operand；以下語意均為
  附加註記並標示推論等級。
- 本輪新增交叉驗證命令（`fd2-cap-local`、Capstone 5 Docker）：
  `tools/disasm_le.py FD2.EXE range 0x24c1e 0x24df2` 與
  `tools/disasm_le.py FD2.EXE range 0x11eee 0x122f0`；輸入仍綁定上述
  MD5／SHA-256，位址基準仍為 Capstone 線性位址。

已證實：`0x24c1e` 的兩段計數流程
----------------------------------

- `0x24c4c` 呼叫 `0x15f84`，text index 2；`0x24cad` 再呼叫同一對白
  播放器，text index 3。兩者的文字來源是 `FDTXT_024`，但不代表
  `postbattle_ch23_persist` 已可執行。
- 第一段在 `0x24c61` 呼叫 `0x11cac(1)`，接著在 `0x24c6b` 呼叫
  `0x17aa9(1)`；`EBX` 從 0 累加至 29，共 30 次。`EDI` 從 2 開始，
  每段結束時在 `0x24c81` 呼叫 `0x24d22(EDI)`，直到 stage 9。
- 第二段在 `0x24cc1..0x24ce7` 迴圈 12 次：先以 raw PUSH 順序
  `[ESI,255,0]` 呼叫 `0x11d40`，再 `0x11cac(0)`、`0x17aa9(1)`；
  `ESI` 每次加 1，因此其正式參數是 `(start=0,end=255,delta=0..11)`。
  `EDI` 於每段結束在 `0x24cf2` 呼叫 `0x24d22(EDI)`，stage 為 10..14。
- `0x24cff` 透過 `0x375c0` 將 `0xa0000` 起點的 `0xfa00` bytes 清零，
  接著 `0x24d13` 呼叫 `0x11506`，`0x24d18` 遞增章節。這個尾端順序是
  已證實的 sync／chapter 行為，不等於已證實的戰間整備消費端。

已證實：`0x17aa9(1)` 是 BIOS tick 等待
----------------------------------------

- `0x17aa9` 讀取 `[0x46c]`，以 `dword_53A2C` 保存前次 tick；差值小於
  immediate `1` 時持續輪詢，並處理 `0x10000` wrap。其時間單位是 DOS
  BIOS tick（約 54.9 ms），不是固定 60 Hz frame。
- 重製編譯器已有 `0x17aa9` 正整數 immediate → editable `delay` 的通用
  lowering（每 tick 以 3 個重製 frame 表示）；這只固定等待原語，不代表
  ch23 的完整 renderer 時序已閉合。

已證實：`0x11d40(0,255,ESI)` 是 12 次完整 DAC 範圍更新
--------------------------------------------------------

- `0x11d40(start,end,delta)` 逐一讀取 `dword_53A65 + 3*index` 的 RGB
  三元組，減去 `delta`、負值夾到 0，再寫入 VGA DAC ports `0x3c8/0x3c9`。
- ch23 的直接指令在 `0x24cc1` 先 push `ESI`、`0xff`、`0`；因此 formal
  參數是 `(0,255,ESI)`，而不是 raw PUSH 順序看似的 `(ESI,255,0)`。
  `ESI=0..11` 是由同一個 12 次迴圈直接遞增所得（已證實）。
- 每次 palette 更新後仍有 `0x11cac(0)`、`0x17aa9(1)` 與
  `0x24d22(EDI)` 的相鄰時序；重製端現以兩個嚴格驗證的
  `native_ch23_loop` 可編輯 beats 保留這 12 組 register-bound palette、
  重繪、tick 與 latch setter 的原始位址。執行器在沒有 indexed／latch
  adapter 時明確失敗即關閉，因此仍不建立 `postbattle_ch23_persist` binding。
- `0x4dfcc` 讀取線性位址 `0x60003` 的 31 組 RGB 三元組；其
  `byte_60002=0..15` 以 `3*phase` 為起點，將連續 16 組寫入 DAC
  `0xe0..0xef`。IDA 偽代碼的 `BYTE1(v2)=-32` 與 Docker Capstone 的
  `mov ah,0xe0`／`out dx,al` 共同固定這個高位索引；舊的低位索引
  說法已撤回。重製端 `ApplyNativeCh23PaletteCycle` 保留這個固定視窗
  與原始位址來源；它是 raw palette 原語，不代表完整 palette 時序已接通。

已證實：保留原始名稱的 `0x24d22` raw staging 分支
--------------------------------------------------

- `0x24d22..0x24df2` 在 `arg != 0` 時只將低位元組寫入 `byte_51A10` 後返回；
  ch23 只傳入非零 stage 2..14，因此本 handler 不會走 `arg == 0` 分支。
- `arg == 0` 另配置 `latch*0x138` bytes，從
  `0x53aff + (0xc0-latch)*0x138` 複製，再由 `0xbf-latch` 向 0 倒序複製
  0x138-byte rows，最後釋放暫存區。這是獨立的 copy branch，不能泛稱
  淡入淡出或 indexed renderer。
- IDA 的直接資料交叉參照仍只在 `0x24d22` 內顯示寫入／讀取；但沿著
  `0x11cac→0x11eee` 的控制流程追查可見 `dword_53C03==23` 分支在 BIOS
  tick 改變時呼叫 `0x24d22(0)`。因此已證實存在間接消費端，`0x51a10`
  可附加註記為「312-byte staging 的列旋轉 raw latch 值」（已證實），
  但仍不可命名為 frame、palette 或一般畫面狀態。

已證實：`0x11cac→0x11eee` 透過 case 23 間接消費 raw latch
---------------------------------------------------------------

- IDA Pro 9.4 的 `0x11cac(a1)` 先更新 native tick/pose 狀態，只有
  `a1==0` 額外呼叫 `0x4dfcc`；兩個參數值之後都進同一條 indexed 路徑：
  `0x11eee(dword_53a49+32904,456,13,8,dword_53aa9,dword_53aad)`、
  `0x122dc`、`0x127a9`、`0x1acf3`，最後由 `0x11eb0` 把
  `312×192` bytes、stride `456` 的 staging copy 到 VGA。
- `0x11cac` 本身沒有直接讀取 `0x51a10`；然而它呼叫的 `0x11eee` 在
  `dword_53C03==23` 且 BIOS tick 改變時呼叫 `0x24d22(0)`，該分支以
  `0x138`（312）byte rows 對 `0x53aff` staging buffer 做列旋轉。因此
  `0x24d22` 的 setter／copy branch 是同一個 raw staging contract 的兩個
  入口，仍不可把它提升成泛用畫面幀或 palette index。
- Docker Capstone 逐指令核對 `0x11eee` 的 case 23 分支：`0x11eff` 讀
  signed BIOS tick `[0x46c]`，`0x11f07` 與 `[0x539f8]` 比較；`0x12096`
  只在 raw chapter `[0x53c03]==0x17`（十進位 23）進入此路徑，`0x120a7`
  再次檢查 tick，只有不相等時才由 `0x120af→0x24d22(0)`，接著
  `0x120b9` 把新 tick 寫回 `[0x539f8]`。因此「tick gate 完全未知」已
  撤回；已證實的 gate 是 BIOS tick 變化，不是固定影格延遲。
- 同一分支在 `0x120c6..0x120fe` 將 `0x53aff` staging、`0x138` raw
  row stride 與 `0xc0` rows 傳入 `0x11eb0`。這只證明 case 23 的
  staging present 參數形狀；`0x53aff` 的建立／擁有者、呈現目的地的完整
  位址生命週期與入口 latch 初值仍未知，不能由 `nativeMapWork` 或 PNG
  framebuffer 代替。
- IDA Pro 9.4 的 `0x11cac` 函式本體也固定了 indexed 消費鏈：
  `0x11eee` 後依序呼叫 `0x122dc`、`0x127a9`、`0x1acf3`，再由
  `0x11eb0` 以 `312×192`、stride `456` 複製到 VGA；所有 caller 的
 直接交叉參照包含 ch23 的 `0x24c63` 與 `0x24cd3`。因此本檔不再把
  indexed frame／重繪消費鏈標記為未知；但這只證明靜態共用消費鏈，
  不代表重製執行器已具備其 raw state／latch adapter。
- 這也固定了兩段 ch23 loop 的差異：第一段使用 `0x11cac(1)`，第二段
  使用 `0x11cac(0)` 並額外觸發 `0x4dfcc`；兩者不可在可編輯腳本中折疊
  成同一個 generic redraw。重製端現已提供 `RotateNativeCh23Rows`、
  `ApplyNativeCh23PaletteCycle` 兩個 raw 原語，以及保留完整 call-site／
  stage 值的 `native_ch23_loop` 候選 beats；共用 indexed 消費鏈已由 IDA
  靜態閉合；handler 入口的初始 latch、`dword_53C03` 生命週期、
  `0x53aff` staging 擁有者／呈現目的地、raw state adapter 與一般玩家 E2
  仍未閉合，故仍不建立
  production binding。

限制與目前判定
--------------

- 本檔是 E1 靜態證據；尚無未修改一般玩家 DOSBox 戰後→整備／存檔的 E2
  路徑，也尚未閉合一般玩家入口的 latch／tick 狀態生命週期。
- `postbattle_ch23_persist → preparation_ch24 → story_ch24` 的 campaign
  邊界保留；沒有以 generic town、靜態 palette 或猜測性 `indexed copy`
  取代原版流程。
- 目前仍 fail-closed。帶原始位址、12 次 loop 順序與 raw latch／tick
  provenance 的候選已保存於
  [`ch23_post_candidate.json`](../../../remake/assets/cutscenes/bindings/ch23_post_candidate.json)
  並有 compiler／runner regression；下一步是把已證實的共用 indexed 消費鏈
  接到有 raw provenance 的 state/latch adapter，再以一般玩家路徑驗證後，
  才可評估 production binding。
