FD2.EXE：raw ch22 post／玩家第23戰戰後處理器證據
================================================

輸入基準
--------

- 檔名：FD2.EXE
- 大小：357074 bytes
- MD5：b97caf2239a27a896069d03549d96e1e
- SHA-256：222b7d067ad4450eb9c5f6e6bce1797d54bb050417ba39ced6067f8039f28c4f
- 第一順位工具：IDA Pro 9.4，Docker 內資料庫線性位址
- 第二順位驗證：Capstone 5 Docker，`tools/disasm_le.py` 線性位址
- 本批 IDA 函式：`0x24754`、`0x24b14`、`0x24bde`、`0x2189a`、
  `0x219ad`、`0x24b4d`、`0x11df2`、`0x4dbfc`
- 註記方式：保留 IDA 原始名稱、線性位址與 raw operand；以下語意均為
  附加註記並標示推論等級。

已證實：`0x24754` 的戰後控制流程
----------------------------------

- `0x247b4` 先以 `0x233c6` 建立 16×17 的配置／場景資料，之後以
  `0x24b14(100)` 掃描 16 個原生單位索引。成功與失敗分支都保留原始
  對白與 acting 位址：`0x15f84` 的 text index 8／9、`0x1366a(71)`。
- 直接指令在 `0x247c6` 比較 `0x24b14` 回傳值與 `-1`，`je 0x247fb`；
  因此回傳不是 `-1` 才播放 text index 8／JOIN22，回傳 `-1` 才播放
  text index 9／`0x1366a(71)`。這個方向由原始跳轉固定，不由角色名稱推測。
- 接著以 `0x24bde(18)` 檢查 persistent record；成立時播放 text index 10、
  `0x1366a(72)`、`0x32975(17)` 與 text index 11。不成立時再以
  `dword_53BEF < 15` 分支到 text index 13／`0x112a5(19)`，否則播放
  text index 12、`0x1366a(72)`、`0x32975(17)`。這些是控制流程與 raw
  呼叫的已證實描述，不替 record 或角色建立未證實名稱。
- 共同尾端為 `0x11506`、章節遞增、text index 14、400 ms 等待，接著依序
  呼叫 `0x2189a(10,15,1)`、`0x24b4d(30)`、text index 15、400 ms、
  再呼叫 `0x2189a(10,15,1)`、`0x24b4d(30)`、text index 16、400 ms，
  最後呼叫 `0x2189a(16,30,1)`。
- 以上只證明原版 handler 的靜態順序；`postbattle_ch22_persist` 尚未因此
  取得正式執行 binding，也沒有把下一節點猜成城鎮或下一場戰鬥。

已證實：`0x24b14(100)` 與 `0x24bde(18)` 的 raw 條件
------------------------------------------------------

- `0x24b14(int a1)` 逐一以 `i=0..15` 呼叫 `0x31860(i,a1)`，任一回傳
  非零即回傳 `1`，否則回傳 `-1`。目前只保留「16 索引掃描／100 的原始
  參數」語意，未把它命名成敵人、物品或角色查詢。
- `0x24bde(int a1)` 迭代 persistent record count `[0x53BFB]`，比較每筆
  record 的 raw byte `+8` 與 `a1`，找到 18 回傳 `1`，否則 `0`。這是
  raw persistent membership 條件；record 格式與玩家可見角色意義仍屬未知。
- `0x24840` 的 `test eax,eax; je 0x248b5` 固定「找到 18」分支；未找到
  才到 `0x248b5` 的 raw `cmp dword [0x53BEF],0xf`。`jl 0x24902` 代表
  `[0x53BEF] < 15` 時播放 text index 13／JOIN19，否則播放 text index 12、
  ACTING72 與 deactivate slot17。這三個比較位址已附加到 editable `if` beats，
  但 `[0x53BEF]` 的高階名稱仍未知。

已證實：`0x2189a` 的十次索引呈現呼叫形狀
--------------------------------------------

- IDA 偽代碼與 Capstone 指令共同固定：函式配置約 `0x25680` bytes 的
  暫存工作區，在 `work+0x8088` 以 `0x11eee(...,456,13,8,...)`
  建立 13×8 的原始地圖／場景資料；外層迴圈以 `i=0..9`、共 10 次執行。
- 每次迴圈以 caller 的第九個原始參數作步進來源（`step_source=caller_arg9`），
  工作區 stride 為 456。`0x21955` 呼叫 `0x219ad` 時保留
  `EDI,192,0,12,ESI,[esp+0x18],[esp+0x18]` 的七個 raw 引數形狀；
  `0x2195d` 呼叫 `0x127a9`；`0x21986` 呼叫 `0x11eb0`，保留
  `192,456,312,work+0x8088,320,0xa0504`；最後 `0x219a3` 呼叫
  `0x11cac(0)`。
- `Native2189ALoop` 只把上述 call-site、重複次數、幾何常數與 raw 引數
  放入可編輯腳本；沒有把它命名成肖像、特效、過場或玩法。重製執行器
  對 `native_2189a_loop` 目前明確回報「indexed adapter 未完成」並停止，
  因此不會以猜測的 generic renderer 取代原始效果。
- `0x24b14`、`0x24bde` 與 `[0x53BEF] < 15` 已在
  `ch22_post.json` 轉成 `native_inventory_item_present`、
  `native_persistent_identity_present` 與 `native_round_lt` 結構化條件。
  這些條件只消費完整 raw inventory／persistent provenance；缺少 raw bytes
  時 runner 失敗即關閉，不退回 normalized inventory 或角色名稱。
- `ch22_post.json` 的 `diagnostics.unknown_ops` 現為 5（兩個 `0x24b4d`、
  兩個 `0x11df2`、一個 `0x4dbfc`）；原先的 10 是條件與 `0x2189a` 尚未
  結構化前的歷史計數，不再作為現況斷言。
- ch22 的三個 caller 位址為 `0x24978`、`0x249c4`（raw
  `[10,15,1]`）及 `0x24a10`（raw `[16,30,1]`）。三個 payload 都在
  `remake/assets/cutscenes/handlers/ch22_post.json` 保存。

已證實：相鄰 raw 原語
----------------------

- `0x24b4d(30)` 以 `0x11eee` 重建 staging，再以 `0x11eb0` 交替呈現
  兩個 stride 456 的 312×192 區塊；每次呈現後等待 20 ms，共 30 次。
  這是雙緩衝／列呈現的 raw 時序，不命名成淡入淡出或特定動畫。
- `0x11df2(start,end,delta)` 的 Capstone／IDA 交叉驗證固定 DAC 索引
  0..255 的逐色分量加法與 63 夾限；ch22 後段的 raw 呼叫
  `0x11df2(ebx,255,0)` 仍保留 register provenance。
- `0x4dbfc` 對 `dword_53A51` 的原始欄位逐筆清除／遮罩；目前只保留 raw
  初始化描述，沒有把它提升成地圖、單位或存檔語意。

證據等級與限制
--------------

- 上述函式邊界、直接呼叫、迴圈次數、引數順序與幾何常數是 E1 靜態「已證實」；
  IDA 與 Capstone 都以同一份固定雜湊的 FD2.EXE、線性位址基準產出。
- `0x24b14`／`0x24bde` 的 record 高階意義、`0x2189a` 的畫面用途、
  raw 工作區生命週期，以及 `postbattle_ch22_persist` 的一般玩家入口，
  仍是強推論或未知；不得以這份檔案升格為 E2。
- 尚無未修改一般玩家 DOSBox 的第23戰戰後→城鎮／商店／整備／存檔擷取，
  也尚未證明 `town_ch23` 的實際節點。原有戰間邊界保持 fail-closed，待
  raw indexed adapter 與一般玩家路徑證據閉合後才可建立正式 binding。
