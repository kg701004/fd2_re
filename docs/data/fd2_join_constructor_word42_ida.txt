FD2 JOIN 角色建構器 `0x112A5` 與 `+0x42/+0x46`（IDA Pro 9.4）
=======================================================================

輸入與工具
----------

- `FD2.EXE`，357074 bytes
- MD5 `b97caf2239a27a896069d03549d96e1e`
- SHA-256 `222b7d067ad4450eb9c5f6e6bce1797d54bb050417ba39ced6067f8039f28c4f`
- IDA Pro 9.4 以 `fd2-ida-authorized-local` 一次性、無網路 Docker 容器
  確認函式邊界、交叉參照與直接資料流；Capstone 5.0.3 覆核指令。
- 本文保留 IDA 線性位址與原始 `sub_` 名稱；語意是帶等級的附加註記。

已證實的資料表
----------------

- `sub_4E4E8(id)` 返回 `0x61DA1 + id*0x18`：32 列、24-byte 角色預設。
- `sub_4E4D1(id)` 返回 `0x620A1 + id*0x0B`：32 列、11-byte 成長列。
- `sub_112A5(id)` 以 `[0x53BFB]` 當 append index，寫入
  `[0x53BF7] + index*0x50` 的新 persistent record。

已證實的 JOIN 公式
--------------------

令 `D` 為 24-byte 角色預設、`G` 為 11-byte 成長列、
`L = D[2]`：

- `0x112EE..0x1130A`：`maxHP = u16(D+3) + G[6] * (L-1)`。
- `0x1130E..0x1131B`：`maxMP = u16(D+5) + G[8] * (L-1)`。
- `0x11337..0x11395`：前兩格固定以 `flag=0x40` 裝備 `D[0x0C..0x0D]`；
  後四格取 `D[0x0E..0x11]`，item `0xFF` 時 flag 為 `0x80`，否則為0；
  最後兩格的 flag 固定為 `0x80`。
- `0x11399..0x113CE`：複製 `D[8..11]` 到 command bytes `+0x1A..+0x1D`，
  清 `+0x1E` 與六個 `+0x22..+0x27` bytes，並寫 `+0x31=0xFF`。
- `0x113D5..0x113E8`：`baseAP = u16(D+0x12) + G[0] * L`。
- `0x113EC..0x11400`：`baseDP = u16(D+0x14) + G[2] * L`。
- `0x1140E..0x11422`：`baseDX = u16(D+0x16) + G[4] * L`。
- `0x11426..0x1142E`：current/max HP 同時寫入 `+0x40/+0x42`。
- `0x11432..0x1143A`：current/max MP 同時寫入 `+0x44/+0x46`。
- `0x11444` 呼叫 `sub_1145A`，再依八個物品格重算
  `+0x48/+0x4A/+0x4C/+0x4E` 衍生數值。

凱麗勘誤
--------

- 角色 id 12 的原始預設位於 `0x55CC1`：`L=10`、base HP=52。
- 對應成長列位於 `0x55F25`：`G[6]=11`。
- 因此新 JOIN record 的 `+0x42 = 52 + 11*(10-1) = 151`。
- `remake/assets/scenarios/ch27.json` 的 `hp=90` 是舊戰役產生器以平均成長
  製作的近似投影，不是 ch27 實際 persistent record，也不是 JOIN 原始值。
  不得把 90 反填成 `native_record_word42`。

重製缺口與等級
----------------

- 上述表位址、JOIN 公式、writer 與凱麗新 JOIN 的 151：**已證實**。
- ch27 一般玩家路徑當下的凱麗 `+0x42`：**未知**；它受先前戰鬥升級、
  轉職與存檔狀態影響，不能由章節號或目前情境 HP 猜出。
- `tools/sync_native_join_constructor.py` 現把兩份 raw 表與
  `fd2-reference-files.json` 轉成 `remake/assets/data/native_join_constructor.json`；
  每列保留原始 file offset、24/11-byte raw rows、FD2.EXE identity 與證據等級。
- `campaign.NativeJoinConstructorTable` 驗證 32 列順序、offset、stride 與雜湊，
  正常 `JOIN→LOADCH` 及 `scenario join_party` 首次建檔共用同一 materializer。
  它先在局部 0x50-byte transaction record 寫入已證實欄位，再呼叫既有
  `battle.ApplyNativeEquipmentRecalc` 執行 `sub_1145A`。任何已裝備 item row
  缺失時整筆失敗，不發布部分 `Unit`。
- `sub_1145A` 的八物品格、`flag&0x40` gate、item row `+1/+5/+3/+7`、
  signed 16-bit accumulation 與 `+0x48/+0x4A/+0x4C/+0x4E` writers：**已證實**。
  凱麗 fresh JOIN 的 base AP／DP／DX 為 `80/69/10`；items `0x3E/0xAC`
  重算後 AP／DP／HIT／EV 為 `100/79/110/15`。
- 局部 transaction record 只承載 `0x112A5→0x1145A` 已寫入或已消費欄位；
  不宣稱保存原版 0x50-byte record 中未觸及 bytes。
- 直接跳章仍沒有先前升級／轉職／存檔歷史，不能冒充正常玩家路徑。
