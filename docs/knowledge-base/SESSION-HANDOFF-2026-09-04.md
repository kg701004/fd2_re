## A.1 又確認的差異(第 6 項)

| 差異 | 成因 | 等級 |
|---|---|---|
| **doc03 的 AP `+0x37` vs 實測 `+0x48`** | **不是矛盾,是兩組不同欄位**。constructor `0x10c50` 對同一筆記錄寫入:`+0x37/+0x39/+0x3b/+0x3e` 是**基礎** AP/DP/MV/DX,`+0x48/+0x4a/+0x4c/+0x4e` 是**生效值**(狀態卡顯示這組) | 靜態 RE + 原版實機 |

**而且它獨立解釋了 HPcur/HPmax 為何標反兩天**:constructor 把同一個值同時寫進

所以任何拿新生/滿血單位做的欄位對照都不可能分辨那兩個 offset。

**MV 解除封鎖**:`+0x3b`(u8,flat)讀到索爾=4 與卡片 `MV·04` 相符,寫入 20 後

## A.7 本附錄期間新增的教訓

1. **「戰鬥資料已存在」≠「玩家可以操作」**——前者讀記憶體就成立,後者要用該層自己的
   函式斷點證明。
2. **否定有兩種**:「不成立」與「時機未到」。用一個布林值回報會讓呼叫端猜錯。
3. **重複量測得到相同答案,在有自走呼叫點時不構成佐證**——它會穩定地給出同一個錯值。
4. **在函式入口讀呼叫框不可靠**(call 會被跳進);正確原語是在**呼叫點**下斷點。
5. **工具應該說「我現在讀不到」**,而不是給一個看起來正常的錯數字。今天幾乎每個假結論
   都是後者:靜態表的 index、`???` 顯示、四筆假命中、0/25 的試驗。

## C.12 ⚠ 方法上的重大更正:退回 DOS 是**機率性**的,而我一直用 n=1 在下因果結論

C.10 之後的整條調查(階梯 A-G、`--mv 0`、`--dest`)都建立在一個沒有言明的假設上:
**同樣的條件會得到同樣的結果**。這個假設是錯的。

### 打破它的觀察

`--dest computed --mv 4 --attack` 是刻意設計的「應該會死」對照組,結果**跑滿三回合存活**。
而完全相同的條件先前在 **6 個不同實例上死了 6 次**(sfx2/win3/ctl2/ctl1/lad1/lad2)。

| 條件 | 觀察 |
|---|---|
| `--attack --mv 4` | 死 6 次 |
| `--mv 0 --attack` | 活 1 次 |
| `--dest computed --mv 4 --attack` | 活 1 次 |

### 這讓先前哪些結論失效

* **「移動被指認」(來自 `--mv 0` 存活)不成立。** 那是單次觀察,而同一條件現在也會存活。
* **階梯 A-G 的「已排除」強度遠低於我寫的。** 若崩潰是機率性的,「8 輪全活」不構成排除——
  它只是沒觸發。我在 C.11 之後寫的「六階全部排除」應讀成「六階在該次取樣下未觸發」。
* **C.10 的同實例對照仍然成立**(不含攻擊活、含攻擊死),但它同樣是 n=1,
  只能說明傾向,不能定量。

### 正確的做法

**同一條件重複多次、比較發生率**,而不是比較單次結果。這需要:
1. 每個條件跑 N 次(N 至少 5),記錄死亡率。
2. 每次都從**相同的起始狀態**開始——目前 par2 那次存活時,戰場狀態已被前一次
   `--mv 0` 執行改變(敵方剩 4),所以連「相同條件」都不完全成立。
3. 這使**存檔狀態快照**從「加速手段」升格為**方法上的必要條件**:
   沒有它就無法讓每次重複都從同一個狀態開始。而它目前卡在 mapper 收不到合成按鍵
   (C.11),唯一未測的殘餘是自訂 mapper 檔綁單一按鍵。

### 我應該更早發現

線索一直都在:失敗的 log 裡反覆出現「等不到可操作狀態」「行動未生效,重試一次」,
而**成功的執行也有同樣的訊息**。同一個輸入序列會走到不同狀態,本身就是非決定性的證據。
我把它讀成「時序抖動」,沒有推論到「那麼結果也可能抖動」。

C.12 說「要從相同起始狀態重複多次」,並把快照列為必要條件。快照不通,但**並行直接解決

## C.15 更正:昨晚提交的「EIP 修正解決了 10 次全滅」是誤判因果

`d3cb3e10` 把 `H.read_eip()` 的一致化寫成「修好了 10 次試驗全滅的成因」。
**那不是真的**——`read_eip` 的修正是真實且值得保留的(它防的是一個真的存在的脆弱模式),
但**不是**這次全滅的原因。修好之後重跑,10 次試驗**一模一樣地全滅**,同一個 IndexError。

### 真正的根因:裸 `"bash"` 解析到 WSL 轉接器,不是 Git Bash

驅動腳本自己的 `2>&1 | tail -1` 把每一份 Python traceback 都截成一行,所以先前
只看得到 `IndexError: list index out of range`,看不出從哪裡丟的。做一份不截斷的
副本重現,traceback 顯示 `File "/mnt/c/Users/kg701/.../fd2_dosbox_live_helper.py"`
——那個 `/mnt/c/` 開頭代表跑這段的是 **WSL 自己的 python3**,不是 Windows python.exe。

直接測試證實:`subprocess.run(["bash", ...])` 從 Windows python.exe 呼叫時,
在這台機器上解析到 `C:\Windows\System32\bash.exe`(WSL 轉接器),不是 Git Bash——
即使互動式 shell 的 `where bash` 顯示 Git Bash 排第一。那個排序只在**互動式 shell**
裡成立(PATH 被 Git Bash 的啟動腳本改過);`subprocess.run` 繼承的是未經修改的
原始環境 PATH,System32 在那裡排更前面。**這是確定性的,不是機率性的**——只是
我先前手動用互動式 Bash 工具重現時,那條路徑天生解析到 Git Bash,一直測不出來。

而且這不只是路徑轉換寫錯:**WSL 裡面根本沒有 `wsl` 這個指令**(`which wsl` 空手而回)。
一旦執行流跑進 WSL,`fd2_dosbox_live_helper.py` 幾乎每個函式都靠 `wsl -d Ubuntu ...`
往外呼叫——這條鏈路結構性地走不通,不是修一行路徑轉換就夠。

### 處置

* `_to_wsl_path()`/`to_wsl_path()` 改成兩種輸入(Windows 路徑、已經是 POSIX 路徑)
  都認得,不假設只有一種。
* 新增 `H.GIT_BASH`:明確定位、排除 System32,`fd2_trial_runner.py` 的 `drive()`
  改用它,不再賭 PATH 的解析順序。
