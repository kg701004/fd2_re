## 7. 本輪反覆踩到、值得後人避開的坑

1. **含反引號的長文不可當 shell 參數**傳給 `worklist_status --append`:bash 會做命令替換,
   寫進檔案的那一行**所有反引號片段都會消失**。用 heredoc 或檔案。
2. **不可中途砍掉突變測試**:`verify_selftest_discrimination` 是就地改寫原始碼再還原的,
   被中斷會留下已突變的檔案,且 `ast.unparse` 會永久刪掉註解與 shebang。已加備份機制。
3. **`verify_everything` 執行期間不可動任何檔案**:audit 會對工作區取指紋,discrim 會就地改碼。
4. **驗證期間也不要下重負載指令**:實測會讓整輪從 ~35 分鐘拖到 ~70 分鐘。
5. **`--mark-reviewed` 的 `file` 參數吃基本檔名**(現已同時接受路徑),舊版失敗訊息會誤導成
   「行號漂移」。
6. **`--diff` 看不到未追蹤檔案**(已修):`git diff` 完全不含 untracked,所以一份**全新的**
   知識庫文件會整份繞過 provenance 閘門。寫這份交接文件時就踩到——閘門報「新增 0 筆」,
   而手動 `classify()` 在同一份檔案上得到 11 筆。修法是把未追蹤的 `.md` 合成 unified diff
   再交給既有解析器(規則自動一致),並加一組成對 selftest(`.md` 必須看見、非 `.md` 必須
   忽略)。修好後它立刻在本文件裡抓到 **9 筆**沒有來源標記的主張,已逐筆登錄為 `benign`。

### 8.1 突變測試的分母量錯了東西(`WEAK` 的意義)

`fd2_chapter_sweep.py` 被判 WEAK(0/12)。我照字面把它當「selftest 不夠力」,替它補了
一整層畫面判準的成對測試(合成影像重建其模組註解記載的歷史誤判)並以故障注入確認有效
——分數只從 0/12 動到 1/12。**問題不在被測工具,在度量本身**:突變落點對**全檔**均勻
抽樣,而該工具 3568 行、57 個函式,絕大多數是 tmux/xdotool/除錯器層,任何離線 selftest
都執行不到。期望捕捉率被**檔案組成**壓在個位數,與 selftest 好壞無關。

`WEAK` 無法分辨「selftest 沒用」與「樣本全落在執行不到的地方」——對立假說預測同樣的
觀測值,於是它把工程力氣導向錯的方向。改法:用 `trace` 量出 selftest 真正執行過的行,
把每個突變依落點分成 (a) 可達且非測試自身的產品碼、(b) 測試自己的輸入或斷言、
(c) 執行不到,並新增判定 **`UNREACHABLE_SAMPLE`** = 這一輪沒有提供任何證據。
逃掉的可達產品碼突變**逐筆列出**,那才是線索。

由此又掉出兩個缺陷:

* **`exit_code_constants` 排除得遠比它宣稱的多**:它把全檔**每一個 `return` 裡的每個常數**
  標為不可突變,於是 `return a + 3`、`return w * 2`、`return v & 0xff` 這類真正的邏輯,
  在**全部 63 支工具**裡從未被突變過——而且看不見,因為被排除的落點根本不會被計數。
* **本工具自己的負向控制從來沒測到它宣稱的事**:那個「盲目」探針是 `def add(a, b): return a + b`,
  裡面一個可突變的產品碼落點都沒有。它得 0 分的原因是**無處可突變**,不是「selftest 什麼
  都不檢查」。兩者觀測值相同、意義相反。

另外修好 `verify_everything` 的跨輪比對:原本只比 `ok` 布林值,現在分成 **UNSTABLE**
(判定翻轉)與**跨輪內容有變**(判定相同、結論變了)兩類,後者印出兩輪原文;
`axis_discrim` 也不再丟棄「弱(…)」那份名單。修好後第一次真實運行就抓到並點名了
先前被吞掉的那個差異。

### 8.2 截斷韌性測試的取樣一直是退化的(3 個真崩潰)

`verify_truncation_robustness` 報「共 9 個解碼器:安全 9 / 崩潰 0」,三層問題疊在一起:

1. **缺列**:5 支工具共用同一個 `6 + n*4 > len(d)` 目錄標頭形狀,守衛旁邊都有 2026-09-08
   的註解、彼此互相點名為「同一輪一併修的姊妹問題」,而那一輪只有 `decode_lmi.lmi_offsets`
   進了表——**不是有人判斷過其他四支不需要,是它們只吃路徑、不吃 bytes,不符合登錄表的
   介面形狀而靜默落榜**。落榜的列不會出現在總數裡。
2. **合法例外清單赦免了要偵測的症狀**:清單比對例外的 `__name__`,而 `struct.error.__name__`
   就是 `"error"`,表裡有兩列寫了它。模組 docstring 自己還寫著「特別是 IndexError /
   struct.error 這種讀過頭的」。
3. **取樣退化**:`_sample()` 取「排序後第一個檔」,而 `FDOTHER_000.bin` 不是 LMI1,於是
   `decode_lmi.lmi_offsets` 自登錄以來 **601 個輸入每一個都停在 magic 那道門**,一行實質
   邏輯都沒跑到卻每輪報 OK;另三列則是被 600-byte 上限砍過的頭,完整取樣自己就先被拒。

修好後抓到 **3 個真崩潰,形狀完全一致(magic 檢查放行後,未檢查長度就讀下一個欄位)**:

| 工具 | 崩潰輸入 |
|---|---|
| `unpack_dat.parse_directory` | 長度 6–9 丟 `struct.error`;另 `first == 6` → `n == 0` → `offs[-1]` 對空 list 取值的 `IndexError` |
| `decode_lmi.lmi_offsets` | 長度 4/5 丟 `struct.error` |
| `dump_remap.parse_lmi_bytes` | 同一份邏輯的第二個實作,同一個洞 |

2026-09-08 那輪的守衛**加深了一層**:管的是目錄內容的界限,管不到讀出筆數這個動作本身。
新增獨立判定 **`DEGENERATE`**(完整取樣自己就被拒 = 這一列測不到東西),不併進 OK 也不
併進 CRASH,且讓整體失敗。故障注入確認它承重:拿掉前提檢查,退化取樣立刻退回歷史上的「OK」。

### 8.3 兩支工具的 selftest 失敗時仍 exit 0

`sync_native_treasures.py` / `sync_native_field_events.py` 的 `__main__` 是裸呼叫 `main()`,
而 `main()` 會 `return selftest()`——回傳值被丟掉,於是 `--selftest` **印出 SELFTEST FAILED
之後仍然 exit 0**。所有以離開碼判斷的呼叫端(`verify_all_tools` 的 selftest 層、突變測試的
基準與捕捉判定)都只看得到通過。**這正是這兩支長期被判 WEAK 的原因:它們的 selftest 不可能
失敗。**

發現的經過值得記:我先補了寶箱表版面的斷言,故障注入卻五個全部「逃掉」。沒有據此斷定
斷言寫壞,而是把單一注入的**完整輸出**印出來看——訊息明明寫著 SELFTEST FAILED,rc 卻是 0。
症狀在離開碼,不在斷言。

`verify_tool_hygiene` 新增 `exit_code` 規則(AST:`__main__` 裡裸呼叫會回傳值的 `main`/
`selftest`),全 repo 掃描確認只有這兩支中招。規則第一版寫成「任何會回傳值的函式」,立刻
誤報 `gtl2wopl`——它的 `build_wopl()` 回傳 `(n_mel, n_perc)` 這種**資料**,丟掉完全正確。
收斂為只看慣例上承載離開碼的兩個名字,並把 gtl2wopl 的形狀放進 selftest 當**負向控制**。

補的斷言刻意不自我實現:寶箱表版面用**兩份反組譯來源的文件值**釘住(doc50 §692 的 `+0x53`
起點、doc25 §957 的 units `0x83` 起點,該文自己寫明 `0x83 = 3+48+32+48`),而不是拿本檔的
算式當答案。五個版面常數逐一擾動,五個全部被抓到。

### 8.7 四個真正開放的 RE 殘留全部解決(`67ab1557..4265ec97`)

§8.0 盤點出 4 項真正開放且離線可做的項目,本輪全部做完。共同的方法特徵是:
**每一項都用兩個不同來源互證,而不是單一反組譯路徑**。

| 項 | 原本的殘留 | 結論 |
|---|---|---|
| **541** | AI 上游的道具選擇評分會不會選到 type-23 道具 | **選不到,但原因不是有閘門**。評分器 `0x1567e` 對道具 type 沒有任何比較(`row[+0x10] > 0xf` 是**夾成 1**,不是排除),唯一過濾是 `row[+0x0d] == 0` 就跳過;而 type==23 的 12 個道具(id 144~155)`+0x0d` 全為 0 |
| **1354** | `0x602ad` table 真正邊界 | **215 列(id 0..214)**。二進位側:位元組指紋掃出 9 個 table 定址器,下一張表在 `0x61646`,上界 218 列;文字側:道具名佔字串索引 181..395,396..409 全空、410 起換類別 —— 兩個獨立來源相容 |
| **1118** | `+0x0b` vs `+0x0c` 的 byte 級細節 | **「通用道具射程欄位」被跨 caller 直接反證**。`0x14818` 有 17 個呼叫端(全部 6 參數),同樣兩個槽:Attack ring 餵 `itemRow[+0xc]`/`[+0xb]`、AI 評分器餵 `itemRow[+0x10]` 與一個布林旗標、`0x1bc3c` 餵兩個字面常數 `1` |
| **857** | `0x627d8` 序列的 byte-pair 欄位語意 | **每組 pair = (單位索引, pose)**。兩條獨立消費路徑都把第一 byte 當單位索引(`[0x53a45] + idx*0x50`)、第二 byte 寫進 `unit[+3]`;而 `unit[+3] = pose` 由**先前已命名**的原語 `0x134e4`(`reset_pose`,本體就是把所有單位的 `+3` 寫 0)佐證 |

**方法上重複踩到的坑(同一天兩次)**:線性反組譯在整段 code 上會失去對齊。
掃 table 定址器時全影像線性掃得到 **0 個**、窄範圍卻有 7 個 —— 那是對齊問題,不是
「不存在」;改用**位元組指紋**掃描後與窄掃一致並多出 2 個。讀 Attack ring 的 push 序時
同樣被咬,改用**多起點收斂檢查**(6 個起點中 5 個在 `0x18e0b` 收斂到同一條指令)確認。

**`--review` 候選 11 → 7**,剩下的 7 個(26/155/447/510/555/848/1042)全部是 §8.0 已
逐一讀過、確認為措辭誤命中的項目,沒有一個是真正開放的工作。

### 8.8 未命名原語 8 → 4:那份「各有記錄理由」的清單本身有問題

§5 把 8 個未命名原語列成「各有記錄理由」,四類理由混在同一行。逐條讀完之後,
**其中三類根本不是封鎖理由**,四個一輪內全部命名完成。

|---|---|
| 「本體未展開」(`0x1c2da`/`0x35f10`) | **還沒有人去看**,不是看不了 |
| 「有合併清理風險」(`0x25089`) | 那是關於 **argc** 的風險,卻被當成不能**命名**的理由——而 `derive_native_argcounts` 自己的 docstring 就寫著「名稱不會帶動參數個數」,兩者是獨立主張 |
| 「文件只提到被呼叫、沒有命名」(`0x361b0`) | 說的是**文件的狀態**,不是**函式的難度**;反組譯後發現它的兩個被呼叫者本來就都已命名 |
| 「doc13 明寫語意未證實」「單一呼叫端」 | 真的是封鎖——證據確實不足 |
